# 01. ディスクという装置

![船の模型をつくる Alice と Bob](../images/01-alice-bob.png)

HDD や SSD のようなストレージは、メモリとは違う。
メモリなら「100 バイト目を 1 バイトだけ読む」「そこに 1 バイトだけ書く」が普通にできるが、
**ストレージはバイト単位でアクセスするものではない**。
読み書きは、決まった大きさの塊単位でしか行えない。

では、どうやって操作するのか。

---

## 1. 装置を用意する

`disk.img` という **1 個のファイルをディスクと見立てて**扱う。
中身は 4 MiB のただの領域で、これを 512 バイトずつに区切って番号を振ったものが、
この章でいう「装置」になる。本物の HDD や SSD、USB メモリでも、以下の考え方は変わらない。

![装置 — 512 バイトのセクタが並んでいるだけ](../images/01-device.svg)

この装置に備わっている機能は 2 つしかない。

- 指定された **n 番地から 512 バイトを読む**
- 指定された **n 番地に 512 バイトを書く**

**セクタ**は装置が扱える最小単位で、ここでは 512 バイト。
この装置に対して「100 バイト目から 30 バイトだけ書く」という要求は存在しない。
30 バイト書き換えたければ、そのセクタを 512 バイト読み、メモリ上で 30 バイト差し替え、
512 バイト書き戻すことになる。これを **read-modify-write** という。

![read-modify-write — 100 バイト目から 30 バイトだけ書き換えたい](../images/01-read-modify-write.svg)

この形は、このあと何度も出てくる。第 3 章でファイルの途中に書き込むときも、
第 4 章でディレクトリのエントリを 1 個消すときも、やっていることは同じ
「ブロックを読む → 一部を差し替える → ブロックを書く」になる。

もう一つ、装置は**空き領域の管理をしてくれない**。
セクタ 7 に意味のあるデータが入っているのか、誰も使っていないゴミなのか、
装置に聞いても答えはない。「全部ゼロなら未使用」も成り立たない
（ゼロが正しいデータであることもある）。

---

## 2. 問題 — テキストを 2 つ保存したい

`memo.txt`（1200 バイト）と `notes.txt`（800 バイト）を保存したい。
装置しかない状態で、これをやろうとすると何が起きるか。

まず `memo.txt`。1200 バイトはセクタ 3 個分（1536 バイト）に収まる。
先頭から詰めて、セクタ 0, 1, 2 に書く。次の `notes.txt` はセクタ 3, 4 に。
ここまでは動く。問題はそのあとに出る。

![素朴に詰めると何が起きるか](../images/01-placement-problem.svg)

**問題 1: 対応を覚えているのは誰か。**
「`memo.txt` はセクタ 0–2、長さ 1200 バイト」という情報は、
どこにも書かれていない。プログラムの変数に入れておくことはできるが、
プログラムが終われば消える。電源を切れば消える。
次にこのディスクを開いたとき、そこにあるのは**意味の分からない 4 MiB の数字の列**でしかない。

**問題 2: 長さが分からない。**
`memo.txt` は 1200 バイトなのに、セクタ 3 個分 = 1536 バイト読める。
残り 336 バイトはゴミ。「ここまでが本文」と教えてくれるものがない。

**問題 3: 削除すると穴があく。**
`memo.txt` を消すとセクタ 0–2 が空く。そこに 4 セクタ必要なファイルは入らない。
空きは合計すれば足りているのに、**連続した空きがない**から置けない、という状況が起きる。

**問題 4: ファイルは伸びる。**
`notes.txt` に追記したくなっても、隣のセクタ 5 は別のファイルが使っているかもしれない。
「ファイルは連続した領域に置く」という前提は、追記があると簡単に壊れる。

---

## 3. 答えの形 — 管理情報もディスクに置く

問題 1 の答えがすべての出発点になる。
「どこに何があるか」を覚えておく場所が要る。そしてそれは、
電源を切っても残らなければ意味がないので、**ディスクの中**でなければならない。

![管理情報をディスクの中に置く](../images/01-metadata-on-disk.svg)

つまり 4 MiB のうち一部を、ファイルの中身ではなく**管理情報 (metadata) を置くため**に使う。
管理情報が自分自身の配置も説明していれば、次に開いたときもう一度構造をたどれる
（**自己記述的**である、という）。

この「ディスクの一部を管理情報に割き、残りをデータに使い、
その上に名前やディレクトリの仕組みを乗せたもの」が**ファイルシステム**。
つまりファイルシステムは、装置が持っていない機能を**ディスク上のデータ構造で**埋める仕掛けにすぎない。
カーネルの中にある特別な何かではなく、バイト列の設計の問題として扱える。

これから決めるのは、結局この 3 つ。

1. **空き管理** — どのブロックが使用中か（第 2 章：ビットマップ）
2. **ファイルの表現** — どのブロックがどのファイルの何バイト目か（第 3 章：i-node）
3. **名前** — 人間が使う名前と、その表現の対応（第 4 章：ディレクトリ）

そして「それぞれがディスクのどこに置かれているか」を第 5 章で確定させる。

---

## 4. 扱う単位を決める — セクタからブロックへ

管理情報を設計する前に、単位を決めておく。
以降のファイルシステムは、512 バイトのセクタを直接は扱わない。
**8 セクタ = 4096 バイトを 1 ブロック**として、常にブロック単位で考える。

![8 セクタを 1 ブロックにまとめる](../images/01-sector-to-block.svg)

```python
# ブロック番号 → セクタ番号は掛け算するだけ
first_sector = block_no * SECTORS_PER_BLOCK   # 8
```

4096 バイトを選ぶ理由:

- **管理情報が 8 分の 1 になる。** 空き管理のビットも、ファイルが持つブロック番号の一覧も、
  管理対象の数がそのまま量になる。8192 セクタを管理するより 1024 ブロックを管理する方が小さい。
- **1 個のファイルを少ないポインタで指せる。** 後で出てくる i-node は
  ブロック番号を 12 個しか持たない。512 バイト単位なら 6 KiB までのファイルしか作れないが、
  4096 バイト単位なら 48 KiB まで届く。
- **Linux のページサイズと同じ。** OS がメモリを扱う単位と揃っていると、
  余計な変換が要らない。

代償もある。**1 バイトのファイルでも 1 ブロック (4096 バイト) を消費する**。
これを**内部断片化**という。小さいファイルが多いほど無駄が増える。

この章以降、**セクタという言葉はほとんど出てこない**。
セクタを知っているのは装置を包む層 (`device.py`) だけで、
その上の層はブロック番号しか見ない。

---

## 5. 実装

層は 2 枚。どちらも「上の層を知らない」ので、10 行ずつで終わる。

### `device.py` — 装置のモデル (L0)

```python
class SectorDevice:
    """1 個のイメージファイルを、512 バイトのセクタの配列として見せる。"""

    def read_sector(self, sector_no: int) -> bytes:
        # 範囲外は静かに 0 を返さず、必ず例外で落とす。
        # 「読めてしまう」バグは、後から原因をたどるのが非常に難しい。
        self._check_range(sector_no)
        self._file.seek(sector_no * SECTOR_SIZE)
        return self._file.read(SECTOR_SIZE)

    def write_sector(self, sector_no: int, data: bytes) -> None:
        # 512 バイトちょうどでなければ受け付けない（装置の性質をそのまま守る）
        if len(data) != SECTOR_SIZE:
            raise ValueError(...)
        ...
```

`assert` ではなく明示的な例外を使う。`python -O` で消えてしまう検査に、
ディスクを壊さない責任を持たせてはいけない。

### `disk.py` — ブロックに束ねる (L1)

```python
class BlockDevice:
    """8 セクタを 1 ブロックに束ねて見せるだけの層。"""

    def read_block(self, block_no: int) -> bytes:
        first = block_no * SECTORS_PER_BLOCK
        return b"".join(
            self._dev.read_sector(first + i) for i in range(SECTORS_PER_BLOCK)
        )
```

この層は**何も賢いことをしない**。キャッシュも遅延書き込みも持たない。
`write_block` を呼べば 8 回 `write_sector` が呼ばれ、すぐディスクに届く。
性能のための仕掛けを入れないことで、
「いまディスク上のバイト列がどうなっているか」を常に説明できる状態を保つ。

### テスト

```python
def test_block_roundtrip(tmp_path):
    # 書いたものがそのまま読めること（一番退屈で、一番効くテスト）
    ...

def test_block_is_eight_sectors(tmp_path):
    # ブロック 1 に書いたら、セクタ 8-15 が変わり、セクタ 7 と 16 は変わらないこと
    ...

def test_out_of_range_raises(tmp_path):
    # 範囲外のブロック番号は例外
    ...
```

2 つ目のテストが効く。ブロックとセクタの対応がずれていても
「書いて読む」だけのテストは通ってしまうので、
**装置側から見て正しい位置に書かれているか**を直接確かめる。
