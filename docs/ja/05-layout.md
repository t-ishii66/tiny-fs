# 05. 地図を描く — レイアウトの確定

部品は揃った。ビットマップ (第 2 章)、i-node (第 3 章)、ディレクトリ (第 4 章)。
しかしどれも「自分がディスクのどこに置かれているか」を知らない。
次にこのイメージを開いたとき、**それを誰が教えてくれるのか**が最後の問題になる。

この章で決めるのは 2 つ。

- 4 MiB のディスクを、どの部品にどれだけ割り当てるか（レイアウト）
- その割り当て自体をどこに書いておくか（スーパーブロック）

ここまで来れば、この章だけ読んで別の言語で同じイメージを作り直せる、という状態になる。

---

## 1. 全体像

既定の `TOTAL_BLOCKS = 1024`（= 8192 セクタ = 4 MiB）のときのブロック割り当て。
第 1 章のとおり 1 ブロック = 8 セクタなので、以下はすべてブロック番号で書く。

![tiny-fs のブロック割り当て](../images/05-layout-overview.svg)

先頭 3 ブロックの位置は**固定**（スーパーブロックを読む前に読めないと困るのはビットマップ
ではなくスーパーブロック自身だけなので、本当に固定が必要なのはブロック 0 だけだが、
教材としては「ここを見れば必ずある」方が読みやすい）。
i-node テーブルとデータ領域の開始位置は、スーパーブロックの
`inode_table_start` / `data_start` に書いてあるものを正とする。

ファイルを名前から中身までたどる経路は常にこの 1 本しかない。

![パスから中身へたどる経路](../images/05-lookup-chain.svg)

## 2. 定数

すべて `tiny_fs/constants.py` に置く。**ここ以外に数値を書かない。**

| 定数 | 値 | 導出 / 意味 |
|---|---|---|
| `SECTOR_SIZE` | 512 | 装置が決めた最小単位（第 1 章）。ファイルシステムは直接扱わない |
| `SECTORS_PER_BLOCK` | 8 | 4096 ÷ 512 |
| `BLOCK_SIZE` | 4096 | FS が扱う単位。Linux のページサイズに合わせた |
| `TOTAL_BLOCKS` | 1024 | mkfs で変更可。4096 × 1024 = 4 MiB = 8192 セクタ |
| `INODE_SIZE` | 128 | 4096 ÷ 128 = **32 個 / ブロック**（割り切れることが重要） |
| `NUM_INODES` | 128 | 128 ÷ 32 = i-node テーブル **4 ブロック** |
| `NDIRECT` | 12 | i-node が持つ直接ポインタの数 |
| `MAX_FILE_SIZE` | 49152 | 12 × 4096 = 48 KiB。**間接参照がないのでこれが上限** |
| `DIRENT_SIZE` | 32 | 4096 ÷ 32 = **128 エントリ / ブロック** |
| `MAX_NAME_LEN` | 27 | 32 − 4 (ino) − 1 (NUL) |
| `MAGIC` | `0x74667331` | ASCII で `"tfs1"`。末尾の `1` がレイアウトのバージョン |

`INODE_SIZE` も `DIRENT_SIZE` も `BLOCK_SIZE` の約数にしてある。これにより
**「構造体がブロック境界をまたぐ」ケースが一切発生しない**。
ブロックを 1 枚読めば、その中の要素は必ず完全な形で入っている。

### エンディアンとアライメント

すべて**リトルエンディアン**。`struct` のフォーマット文字列は必ず先頭に `<` を付ける。

```python
# 先頭の '<' には 2 つの意味がある:
#   1. リトルエンディアン固定（実行環境の CPU に依存しない）
#   2. アライメント・パディングを入れない（構造体サイズが手計算と一致する）
# '<' を忘れると、同じイメージが CPU によって違う意味になる。
SUPERBLOCK_FMT = "<IIIIIIII"
```

## 3. スーパーブロック（ブロック 0）

32 バイト。残り 4064 バイトはゼロ。

![スーパーブロックのバイト配置](../images/05-struct-superblock.svg)

`free_hint` は「次に空きブロックを探し始める位置」。あとで述べるとおり、これはヒントにすぎない。

mkfs 直後の実バイト列:

```
00000000  31 73 66 74 00 10 00 00 00 04 00 00 80 00 00 00  |1sft............|
00000010  03 00 00 00 07 00 00 00 01 00 00 00 08 00 00 00  |................|
           ^^^^^^^^^^^ ^^^^^^^^^^^ ^^^^^^^^^^^ ^^^^^^^^^^^
           table=3      data=7      root=1      hint=8
```

**先頭 4 バイトが `31 73 66 74` = `"1sft"` に見える**のが重要な観察点。
`MAGIC` を「4 バイトの文字列」ではなく「32 ビット整数 `0x74667331`」として定義したので、
リトルエンディアンで書き出すと下位バイトから並び、目で見ると逆順になる。
`hexdump` でイメージを覗くときは、この並びで探すことになる。

### 検証

イメージを開くたびに、`fs.py` が次を確認して、合わなければ明確な例外で落とす。

- `magic == MAGIC` — 違えば「tiny-fs のイメージではない」か「バージョンが違う」
- `block_size == BLOCK_SIZE` — 違うブロックサイズは読めない
- `data_start == inode_table_start + ceil(num_inodes / (BLOCK_SIZE // INODE_SIZE))`
  — 自己矛盾したスーパーブロックを弾く

レイアウトを変更したら `MAGIC` を `"tfs2"` (`0x74667332`) に上げる。
古いイメージとの互換は維持しなくてよいが、**静かに誤読するのが最悪**なので、
必ず検出できるようにする。

### `free_hint`

「次はこのブロック番号から空きを探すと速い」という**ヒントにすぎない**。
壊れていても正しさには影響しない（探索がやり直しになるだけ）。
`fsck` はこの値を信用せず、ビットマップを直接数える。

## 4. ビットマップ（ブロック 1, 2）

1 ビット = 1 ブロック（または 1 i-node）。**ビットが 0 なら空き、1 なら使用中**、
ビット順は LSB first。仕組みは第 2 章のとおりで、ここで決めるのは
**その 2 枚をディスクのどこに置き、どの番号から数え始めるか**だけ。

### データブロック・ビットマップは「全ブロック」を覆う

データ領域だけでなく、スーパーブロックやビットマップ自身を含む**イメージ全体**を
対象にする。つまり `ビット番号 == ブロック番号` がそのまま成り立つ。
mkfs はメタデータのブロック 0〜6 を最初から使用中にしておく。

mkfs 直後（ルートディレクトリのデータブロック 7 も割り当て済み）:

```
block bitmap (block 1)
00000000  ff 00 00 00 00 00 00 00 ...   ブロック 0-7 が使用中、8 以降は空き
```

### 余りビットの扱い

1 ブロック = 4096 バイト = **32768 ビット**あるので、`TOTAL_BLOCKS = 1024` なら
先頭 128 バイトしか意味を持たない。残りは 0 のまま置く。

「存在しないブロックを割り当ててしまう」事故は、ビットを 1 で埋めて防ぐのではなく、
**アロケータが `total_blocks` で明示的に走査を打ち切る**ことで防ぐ。
ビットマップの中身は常に「0 = 空き」の意味だけを持ち、dump したときに
余白が特別な意味を持たない方が読みやすいため。
`fsck` は逆に「`total_blocks` 以降のビットが 1 になっていないこと」を検査する。

この方式では、ビットマップ 1 ブロックで最大 32768 ブロック = 128 MiB まで表現できる。
mkfs はこれを超える `--blocks` を拒否する。

### i-node ビットマップ（ブロック 2）

同じ形式。ただし**ビット番号 = i-node 番号**とする（1 始まりのズレを入れない）。
結果として**ビット 0 は永久に使われない**ので、mkfs で 1（使用中）にしておく。
こうすると「i-node 0 は無効」という規約がビットマップ上でも表現される。

```python
# mkfs — i-node ビットマップの初期化
#
# 扱うのは bit 0 .. bit NUM_INODES の NUM_INODES + 1 個。
# ビット番号を i-node 番号に合わせたので bit 0 が余り、そのぶん容量が 1 多くなる。
# ここを NUM_INODES にすると、走査範囲が 0..127 になって ino 128 が永久に割り当たらない。
inode_bitmap = Bitmap(buf, capacity=NUM_INODES + 1)
inode_bitmap.mark_used(0)          # 無効番号。空きとして拾われないよう最初から埋めておく
inode_bitmap.mark_used(ROOT_INO)   # ino 1 = ルートディレクトリ
```

```
inode bitmap (block 2)
00000000  03 00 00 00 ...   bit0 = 予約(無効番号), bit1 = ルートディレクトリ
```

`03` = `0b00000011` で、下位 2 ビットが立っている。
i-node を 1 個作るたびに、このバイト列のどこか 1 ビットが 0 から 1 に変わる。

## 5. i-node テーブル（ブロック 3 - 6）

i-node 1 個の中身は第 3 章で決めた 128 バイトの構造体。
ここで決めるのは、それを**何個ぶん、どのブロックに並べるか**だけになる。

`NUM_INODES = 128`、`INODE_SIZE = 128` なので、
1 ブロックに 32 個、テーブル全体で 4 ブロック（ブロック 3 – 6）。

mkfs 直後、この中で埋まっているのはルートディレクトリの i-node ただ 1 つ。
その実バイト列:

```
00000000  ed 41 02 00 00 00 00 00 00 00 00 00 40 00 00 00  |.A..........@...|
          ^^^^^ ^^^^^ ^^^^^^^^^^^ ^^^^^^^^^^^ ^^^^^^^^^^^
          mode  nlink uid=0       gid=0       size=64 ---+
00000010  00 00 00 00 c0 10 b5 6a 00 00 00 00 c0 10 b5 6a  |.......j.......j|
          +----------  mtime = 0x6ab510c0  ----  ctime
00000020  00 00 00 00 07 00 00 00 00 00 00 00 00 00 00 00  |................|
          +----------  direct[0] = 7, direct[1..] = 0 (未割り当て)
00000030  ... 以降 128 バイトまでゼロ ...
```

- `mode = 0x41ed = 0o040755` — 上位が種別 `S_IFDIR`、下位が `rwxr-xr-x`
- `nlink = 2` — ルートを指す dirent は `.` と、自分自身の `..`。親がないので 2
- `size = 64` — dirent 2 個 × 32 バイト。**ディレクトリのサイズはバイト単位**

### i-node 番号 → 位置

i-node 番号は **1 始まり**。0 は「無効 / 未使用」を表す番兵として予約する。

```python
# ino は 1 始まりなので、テーブル先頭からの通し番号は (ino - 1)
INODES_PER_BLOCK = BLOCK_SIZE // INODE_SIZE          # = 32
block_no = inode_table_start + (ino - 1) // INODES_PER_BLOCK
offset = ((ino - 1) % INODES_PER_BLOCK) * INODE_SIZE
```

| ino | ブロック | ブロック内オフセット |
|---|---|---|
| 1 (ルート) | 3 | 0 |
| 32 | 3 | 3968 |
| 33 | 4 | 0 |
| 128 | 6 | 3968 |

`direct[i] == 0` を「未割り当て」の番兵として使えるのも、レイアウトのおかげ。
ブロック 0 はスーパーブロックなので、データブロック番号として 0 が現れることはない。

## 6. ルートディレクトリ（データ領域の先頭）

ディレクトリの仕組みは第 4 章のとおり。レイアウトの観点で決めることは 2 つだけ。

- **ルートは常に ino = 1**。マウント時にここから木をたどり始める。
  スーパーブロックの `root_ino` にも書いておくが、値は常に 1
  （フィールドを持つのは「自己記述的であること」を優先したため）。
- ルートのデータブロックは mkfs で 1 個だけ確保する。
  データ領域の先頭なので、既定では**ブロック 7**。

mkfs 直後のルートのデータブロック（ブロック 7）:

```
00000000  01 00 00 00 2e 00 00 00 00 00 00 00 00 00 00 00  |................|
          ino=1       "."  ← 残りは NUL 埋め
00000010  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
00000020  01 00 00 00 2e 2e 00 00 00 00 00 00 00 00 00 00  |................|
          ino=1       ".." ← ルートの親はルート自身
00000030  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
00000040  ... 以降はゼロ（size = 64 なのでここから先は「存在しない」）...
```

ルートの `..` が自分自身を指すので、`/..` は `/` になる。
`cd /..` が `/` に留まるのは、この 4 バイトがそうなっているから。

## 7. mkfs 直後のイメージ全景

| ブロック | 中身 | 状態 |
|---|---|---|
| 0 | スーパーブロック | `magic`, サイズ, `root_ino = 1`, `free_hint = 8` |
| 1 | データブロック・ビットマップ | `ff 00 00 ...` (0-7 使用中) |
| 2 | i-node ビットマップ | `03 00 00 ...` (0 予約, 1 = ルート) |
| 3 | i-node テーブル (1-32) | ino 1 にルートディレクトリ、他はゼロ |
| 4-6 | i-node テーブル (33-128) | すべてゼロ |
| 7 | ルートのデータブロック | `.` と `..` |
| 8-1023 | データ領域 | すべてゼロ、未使用 |

この時点で使用中は 8 ブロック、空きは 1016 ブロック。
第 9 章の `dump` は、この表をイメージから機械的に再構成して表示する。

## 8. 容量の算数

既定値（1024 ブロック / 128 i-node）での上限。**すべてレイアウトから決まる。**

| 項目 | 値 | 導出 |
|---|---|---|
| イメージサイズ | 4 MiB | 4096 × 1024 |
| メタデータ | 28 KiB | 7 ブロック |
| データ領域 | 1017 ブロック ≈ 3.97 MiB | 1024 − 7 |
| 1 ファイルの最大サイズ | **48 KiB** | `NDIRECT` × `BLOCK_SIZE` |
| 最大ファイル / ディレクトリ数 | **127** | `NUM_INODES` − 1（ルート） |
| 1 ディレクトリの最大エントリ数 | **1536** | 12 ブロック × 128 エントリ（`.` `..` 含む） |
| 名前の最大長 | 27 バイト | マルチバイト文字なら UTF-8 で 27 バイト以内 |

どちらが先に枯渇するかは使い方で変わる。小さいファイルを並べれば i-node が先に尽き（127 個）、
48 KiB のファイルを並べればデータ領域が先に尽きる（84 個で 1008 ブロック、85 個目の途中で枯渇）。
どちらも `ENOSPC` で返す。
