# tiny-fs 解説ドキュメント 目次

512 バイトのセクタを読み書きできるだけの「装置」から出発して、
その上にファイルシステムを組み立て、最後は FUSE で Linux にマウントするまでを追う。

## この解説の進め方

**完成したレイアウトを先に提示しない。**
「装置にはこれしかできない」→「だからこの機能が足りない」→「こういう仕組みを入れれば解ける」
の順で、必要に迫られて概念を 1 つずつ導入する。
結果としてできあがった配置図は、第 5 章でまとめて確定させる。

各章の形はどれも同じ。

1. **前章までで何ができないか**（問題）
2. **どう解くか**（採る仕組みを 1 つだけ。バイト列 → 意味の対応まで落とす）
3. **実装**（1 モジュール。テストまで）

各章は「この FS がどう動くか」だけを書く。
やり方を並べて比べることはしない。設計の言い訳や、
ext2 など本物のファイルシステムとの比較も持ち込まない。

図は SVG (`docs/images/`)。16 進ダンプは `dump` の実出力をそのまま貼る。
コード断片のコメントは日本語（ソース本体は英語）。

## 前提

- Python 3.11 以上。コアは標準ライブラリのみ。
- macOS で第 1〜11 章まで完走できる。第 12 章の FUSE だけ Docker の Linux が要る。

まず [第 0 章 準備](00-setup.md) で、手元で動かせる状態を作る。
各章の終わりに **試す** があり、その章の内容をコマンドで確認できる。

## 第 I 部 問題から概念へ

装置しかない状態から始めて、ファイルシステムを構成する部品を 1 つずつ導入する。

### [01. ディスクという装置](01-device.md)

| | |
|---|---|
| 問題 | 4 MiB の領域がある。番号を指定して 512 バイト読む / 書くことしかできない。ここにテキストを 2 つ保存したい。**どこに置く？ 置いた場所を誰が覚える？** |
| 導入する概念 | 装置とファイルシステムの境界。管理情報 (メタデータ) を**ディスク自身の中に**置くという発想。セクタ (512 B) をまとめた**ブロック** (4096 B) |
| 実装 | `tiny_fs/device.py` (L0), `tiny_fs/disk.py` (L1) |
| 完了条件 | セクタ / ブロック単位で書いて読むと同じバイト列が返る。範囲外は例外 |

### [02. どこが空いているか — ビットマップ](02-bitmap.md)

| | |
|---|---|
| 問題 | ブロックは 1024 個ある。次にファイルを置くとき、**空いているブロックをどうやって見つける**のか。全部読んで調べるのか |
| 導入する概念 | 1 ビット = 1 ブロックのビットマップ。1 ブロック (4096 B = 32768 ビット) で 32768 ブロック分を管理できるという圧縮率 |
| 実装 | `tiny_fs/bitmap.py` (L2) |
| 完了条件 | 割り当て / 解放 / 全部埋めて `ENOSPC` / 解放したら空き数が戻る |

### [03. ビットマップだけでは足りない — i-node](03-inode.md)

| | |
|---|---|
| 問題 | ビットマップは「使用中かどうか」しか言わない。**どのブロックがどのファイルのものか**、**何バイト目なのか**は誰も覚えていない。ファイルは伸びるので、連続した場所に置き続けることもできない |
| 導入する概念 | 使ったブロック番号を順に並べた一覧を持つ。その一覧とメタデータを 1 個の固定サイズ構造体にまとめる = **i-node**。`direct[12]` による論理オフセット → 物理ブロックの変換 |
| 実装 | `tiny_fs/inode.py` (L3) |
| 完了条件 | ブロック境界をまたぐ read/write。`MAX_FILE_SIZE` + 1 で `EFBIG` |

### [04. 名前をどう付けるか — ディレクトリ](04-directory.md)

| | |
|---|---|
| 問題 | i-node には**名前がない**。人間は `17 番の i-node` ではなく `memo.txt` で呼びたい。さらに数が増えたらグループに分けたい |
| 導入する概念 | 「名前 → i-node 番号」の対応表 = **dirent**。それを並べたファイルが**ディレクトリ**。ディレクトリも i-node を持つ普通のファイルであること。`.` と `..` による木構造 |
| 実装 | `tiny_fs/directory.py` (L4) |
| 完了条件 | 追加 / 削除 / 検索 / 列挙。`.` `..` の削除を拒否 |

### [05. 地図を描く — レイアウトの確定](05-layout.md)

| | |
|---|---|
| 問題 | 部品は揃った。しかし**それぞれがディスクのどこにあるのか**を、次にこのイメージを開いたとき誰が教えてくれるのか |
| 導入する概念 | 先頭ブロックに置く**スーパーブロック**（自己記述するイメージ）、マジックとバージョン検証、レイアウト全体の確定、それを書き込む **mkfs** |
| 実装 | `tiny_fs/constants.py`, `tiny_fs/fs.py` の `mkfs` |
| 完了条件 | mkfs 直後のイメージを 16 進で読み下せる。他人が同じイメージを再現できる |

## 第 II 部 ファイルシステムとして動かす

部品を `fs.py` の 1 枚の API にまとめ、FUSE なしで全操作ができる状態にする。

### [06. パス解決](06-path.md)

`/docs/a.txt` というパスから i-node 番号を得る手順を決める。
ルートから 1 成分ずつ降りる namei、`.` と `..`、`ENOENT` / `ENOTDIR` の出し分け、
親ディレクトリと最終成分の分離。ここは手順の章で、コードは次章。

### [07. `fs.py` を組む — イメージを開いてファイルを操作する](07-fs.md)

ここから実装が主役になる。`fs.py` を上から順に組み立てる。→ `fs.py` (L5)

| 節 | 内容 |
|---|---|
| 1 | **イメージを開く（マウント）** — `FileSystem.__init__`。スーパーブロックを読んで定数と照合し、2 つのビットマップをメモリに載せる |
| 2 | **i-node テーブルへの出入り** — `_inode_pos` / `read_inode` / `write_inode`。ino → ブロック位置を知っているのはここだけ |
| 3 | **パス解決の実装** — `split_path` / `_walk` / `lookup` / `lookup_parent`（第 6 章の手順をコードに） |
| 4 | **ファイルを作る** — `create`。`lookup_parent` → i-node 確保 → dirent 追加 → `nlink = 1` |
| 5 | **読み書き** — `read` / `write` / `truncate`。ビットマップをいつ書き戻すか |
| 6 | **消す** — `unlink`。dirent を消す → `nlink` を減らす → 0 なら `free_inode` |
| 7 | **テスト** |

### [08. ディレクトリ操作](08-dir-ops.md)

ディレクトリを作る・消す・中を見る・名前を変える。**ここが第 II 部の到達点で、
これがそろえば FUSE なしに全操作ができる。** → `fs.py` (L5)

| 節 | 内容 |
|---|---|
| 1 | **mkdir** — i-node 確保 → `.` と `..` を書く → 親に名前を足す。`nlink` は新ディレクトリが 2、親が +1 |
| 2 | **rmdir** — 空であることの判定（`.` `..` 以外に有効なエントリがない）、`ENOTEMPTY`、親の `nlink` を戻す |
| 3 | **readdir と stat** — 一覧と属性。`.` と `..` は実体があるので作り足さなくてよい |
| 4 | **rename** — 同じディレクトリ内の改名、別ディレクトリへの移動、`..` の付け替え、自分の子孫へ移す禁止 |
| 5 | **テスト** |

## 第 III 部 観察と検証

### [09. イメージを覗く — dump](09-dump.md)

バイト列を人間に読める形に翻訳する。読むだけで、イメージは一切変更しない。
→ `dump.py`

| 節 | 内容 |
|---|---|
| 1 | **出力の形** — スーパーブロック / ビットマップ / i-node テーブル / ディレクトリの 4 部構成 |
| 2 | **mkfs 直後を見る** — 8 ブロックと i-node 1 個だけが使われている状態 |
| 3 | **ファイルを 1 個作って差分を見る** — 何が変わり、何が変わらないか |
| 4 | **生バイトを見る** — `--raw` で任意のブロックを 16 進で出す |
| 5 | **実装** — 範囲のまとめ方、`mode` の文字列化 |
| 6 | **テスト** — 出力を固定文字列と突き合わせる |

### [10. 壊れていないことを確かめる — fsck](10-fsck.md)

同じ事実がディスク上に 2 通り記録されていることを利用して、
両方を独立に求めて突き合わせる。検出だけを行い、修復はしない。→ `fsck.py`

| 節 | 内容 |
|---|---|
| 1 | **何を検査するのか** — 重複して記録されている 3 組（ブロック / i-node / `nlink`） |
| 2 | **期待値を作る** — ルートから木をたどって、使用中ブロックと `nlink` を数え上げる |
| 3 | **突き合わせる** — 検査項目と、それぞれが見つける壊れ方 |
| 4 | **報告する** — 出力と終了ステータス。直さない |
| 5 | **実装** — `fsck.py` |
| 6 | **テスト** — わざと壊して、検出できることを確かめる |
